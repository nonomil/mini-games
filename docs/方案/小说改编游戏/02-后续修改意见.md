# 小说改编游戏后续修改意见

## 1. 修改原则

当前项目已经在推进小游戏底座、地图和宿主协议，因此小说改编不能直接抢占共享文件或重写现有游戏。建议按“先契约、再运行时、后内容和接入”的顺序推进。

每次修改都必须说明：修改文件、为什么需要、能证明什么、不会改变什么。没有对应验收点的视觉或 AI 改造暂不进入主线。

## 2. 优先级总表

| 优先级 | 修改内容 | 目标文件 | 价值 | 暂不做的部分 |
| --- | --- | --- | --- | --- |
| P0 | 内容包 schema、示例 fixture、静态校验器 | `host/novel-content-schema.json`、`tests/test-novel-content-contract.mjs`、`content/novel-adaptations/` | 先证明内容可被稳定解析 | 不做通用 AI 生成器 |
| P0 | 剧情状态最小模型 | `games/novel-adventure/story-state.js`、专属测试 | 固定节点、选择、变量和结局行为 | 不做任意脚本表达式 |
| P1 | 一个章节运行时垂直切片 | `games/novel-adventure/` | 让用户真实玩通一章 | 不改四个已有游戏内部逻辑 |
| P1 | 保存恢复和活动返回 | `storage.js`、`activity-adapter.js`、测试 | 支持刷新、中断、重新开始 | 不接卡片系统私有 storage |
| P1 | 真实浏览器验收工具 | `tests/`、`docs/方案/执行计划/小说改编游戏/验收标准/` | 区分浏览器证据与 Node/fixture 证据 | 不把静态加载当通过 |
| P2 | 探索地图剧情包装 | `games/explore-map/` 的局部适配或新增 adapter | 复用现有地图空间表现 | 不把森林路线改成小说专属状态机 |
| P2 | 小游戏活动适配 | `games/novel-adventure/activity-adapter.js`、manifest | 用现有游戏承载一个关键动作 | 不强制四个小游戏连续运行 |
| P3 | AI 辅助生产工具 | `tools/novel-adaptation/`、内容工作区 | 减少人工整理成本 | 不让 AI 成为运行时依赖 |
| P3 | 美术和构建流水线 | `scripts/`、资源 manifest | 支持多作品复用 | 不先投入大量独占美术 |

## 3. 具体修改建议

### 3.1 先增加通用内容包契约

建议先实现这些确定性字段：

- `projectId`、`contentVersion`、`title`、`contentRating`。
- `startNodeId`、`nodes`、`characters`、`quests`、`activities`、`endings`。
- 每个节点的 `nodeType`、`actions`、`conditions`、`effects` 和 `nextNodeId`。
- 资源通过 `assetId` 引用，再由 `assets-manifest.json` 提供路径、类型、尺寸和来源。

校验器至少拒绝：重复 ID、起点不存在、跳转节点不存在、角色不存在、活动未注册、结局不可达、未声明资源、条件字段越界和循环没有退出路径。

### 3.2 先用纯状态函数，再做 UI

`story-state.js` 应先提供无 DOM 的函数：

```text
createStoryState(content, saved)
canEnterNode(content, state, nodeId)
applyAction(content, state, actionId)
recordActivityResult(content, state, result)
isEnding(state)
serialize/restore
```

这样可以用 Node 测试锁定剧情行为，避免把错误藏在点击事件和模板字符串中。UI 只负责渲染状态和派发动作。

### 3.3 保存系统必须可恢复且可降级

建议使用项目私有键，例如 `mini-games-novel-story-v1:<projectId>`，不要读取卡片系统的 Profile、FSRS 或奖励键。存档要带：

- schema/content 版本。
- session 和最近 checkpoint。
- 当前节点、已访问节点、flags、counters、任务和活动结果。
- 最近一次有效更新时间。

损坏、版本不匹配或节点不存在时，优先回退最近 checkpoint；没有 checkpoint 才新建会话，并给出可理解的提示。

### 3.4 活动适配器只传公开数据

活动适配器将剧情活动转换为现有 host v1 的公开 envelope：

- `gameId`：稳定逻辑游戏 ID。
- `sessionId`：剧情活动会话，不由游戏随机覆盖。
- `cardId`：只有活动确实使用卡片时才传；小说非学习活动保持 `null`。
- `payload.returnContext`：项目、场景、任务和返回地址。
- `complete/stop/error`：归一化为剧情可以理解的活动状态。

适配器不能把小说 flags 写进小游戏局部变量，也不能让游戏直接改变剧情结局。

### 3.5 探索地图只做包装，不做第二套剧情状态机

现有 `forest-route.js` 和 `exploration-session.js` 可作为返回上下文参考。后续若接入小说，优先新增适配器或局部字段，不立即把 `forest-route.js` 抽成“大而全”的小说引擎。先用一个清晰的 `storyProjectId/storyNodeId` 证明边界，再决定是否抽象通用地图组件。

### 3.6 第一章只接入一个小游戏

首个章节建议从一个表达最清晰的活动开始：

- 需要英文单词输入时选苦力怕或飞机大战。
- 需要拼音辨音时选拼音赛车，但内容域必须是 `pinyin`。
- 需要对白短语辨析时选网球学英语。

选择依据是剧情动作是否自然，不是“把已有游戏全部展示一遍”。

### 3.7 AI 工具放在构建侧

后续可以新增 `tools/novel-adaptation/`，但工具输出必须是候选 JSON/Markdown，并经过：

1. schema 校验。
2. 原著引用和版权检查。
3. 内容分级和儿童安全检查。
4. 人工确认和版本提交。

没有上述记录时，不允许把 AI 输出作为发布内容。

## 4. 需要保留的现有边界

- 不修改 `host/bridge.js` 以适配小说专属业务字段；需要的上下文放在现有 `payload` 或 adapter 层。
- 不修改 `games/learning-arcade/game.js` 来承载小说剧情。
- 不让小说运行时直接调用卡片系统源码或读取其 storage key。
- 不把拼音内容写入英语章节。
- 不让地图自行结算 XP、FSRS、Profile 或章节解锁。
- 不删除现有小游戏独立入口。

## 5. 决策门

### Gate A：内容契约

通过条件：示例内容包能通过 schema、引用、可达性和结局检查。未通过前不写 UI。

### Gate B：状态机

通过条件：Node 测试覆盖正常选择、条件不满足、活动完成、活动停止、重复动作、刷新恢复、坏存档和三种结局。未通过前不接地图和卡片系统。

### Gate C：浏览器垂直切片

通过条件：真实浏览器完成入口、对话、选择、活动启动、活动返回、刷新恢复、结局、重新开始和 `360x800`。未通过前不批量生产小说内容。

### Gate D：宿主接入

通过条件：使用真实宿主或可复核 fixture 验证 `ready/init/complete/stop/error`，并明确哪些字段由宿主提供。未通过前保持独立模式发布。

## 6. 主要风险和缓解

| 风险 | 症状 | 缓解 |
| --- | --- | --- |
| 范围膨胀 | 一章变成完整 RPG 引擎 | 限定 5-8 场景、一个活动、2-3 结局 |
| 剧情不可玩 | 文本很多但玩家没有行动 | 每个场景必须有动作和结果 |
| AI 幻觉 | 角色、时间线和事实错误 | fact/inference/original 分层 + 人工确认 |
| 版权风险 | 来源和授权无法追溯 | `source-record.json` + 发布前门禁 |
| 存档失效 | 刷新后回到错误节点 | 版本、checkpoint、坏存档回退测试 |
| 接口越权 | 小说或游戏直接写外部状态 | 只走 adapter/host，做文件范围和协议检查 |
| 视觉投入过早 | 大量素材后才发现状态机不通 | 先用占位素材完成真实垂直切片 |
